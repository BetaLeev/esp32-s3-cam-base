# 问题排查原则

## 核心原则

### 1. 先定位问题位置，再动手修复

遇到问题时，**必须先确认问题出在哪里**：

```
问题症状 → 定位位置 → 验证根因 → 修复 → 验证
```

**错误做法**：猜测问题原因，直接修改，不验证效果。

**正确做法**：
1. 观察日志，确认是前端还是后端问题
2. 用最小测试验证（直接访问接口）
3. 确认修复有效后再继续

### 2. 最小化测试，避免同时改多个地方

每次只改一处，验证后再改下一处。

**错误做法**：
- 同时改前端、后端、配置文件
- 改了 5 处代码后才发现问题没解决

**正确做法**：
- 只改一处
- 验证问题是否解决
- 如果没解决，回滚，继续排查

### 3. 用实际测试验证，不靠猜测

遇到问题时：
1. 先用**最小方式**复现问题
2. 观察实际错误信息
3. 再根据错误信息定位原因

**案例**：文件下载失败

```
❌ 错误流程：
- 猜测：URL 编码问题
- 猜测：Vite 代理问题
- 猜测：缓冲区太小
- 猜测：内存不够
- 改了很多地方，问题依旧

✅ 正确流程：
1. 浏览器直接访问 http://ESP32_IP/fs/files?path=xxx
2. 观察后端日志是否收到请求
3. 根据日志定位问题
```

## ESP32 文件下载问题排查

### 症状：前端无法加载图片/音视频

### 排查步骤

**第 1 步：确认后端是否正常**

在浏览器直接访问后端接口：
```
http://192.168.102.158/fs/files?path=目录/文件名.jpg
```

观察：
- 能否下载文件？
- 后端串口是否有日志？

**第 2 步：根据日志判断**

| 日志情况 | 问题位置 | 解决方案 |
|---------|---------|---------|
| 无日志 | 前端没发请求/Vite 代理问题 | 检查前端代码和 Vite 配置 |
| 有 `下载开始` 但 `打开文件失败` | 后端路径解析问题 | 检查 URL 解码、路径拼接 |
| 有日志但无数据返回 | HTTP 响应问题 | 检查 chunked/Content-Length 设置 |

**第 3 步：常见问题**

1. **后端没收到请求**
   - 检查 Vite 代理配置
   - 检查前端请求 URL

2. **路径解码错误**
   - `httpd_query_key_value` 已经自动解码
   - **不要**再调用 `url_decode()`，会导致双重解码

3. **HTTP 响应头冲突**
   - 不要同时设置 `Content-Length` 和 `Transfer-Encoding: chunked`
   - 只用 chunked 传输时不设置 Content-Length

### 成熟实现参考

文件下载推荐用 `httpd_resp_send_chunk` 分块发送：
```c
// 正确做法
httpd_resp_set_status(req, "200 OK");
httpd_resp_set_hdr(req, "Content-Type", mime);
while (发送中) {
    f_read(file, buf, size, &read);
    httpd_resp_send_chunk(req, buf, read);
}
httpd_resp_send_chunk(req, NULL, 0);  // 结束
```

## 排查清单

遇到问题时，按顺序检查：

- [ ] 问题能否在最小环境下复现？
- [ ] 日志显示问题在哪一端（前端/后端）？
- [ ] 每次修改后是否验证了效果？
- [ ] 是否同时改了多个地方？
- [ ] 有没有参考成熟实现/官方示例？

## 教训记录

### 2024-08 文件管理器修复记录

**问题**：图片点击后无法加载

**错误做法**：
- 改前端 Vite 代理
- 改前端 URL 编码方式
- 用 fetch + blob 绕过问题
- 改缓冲区大小
- 改了 10+ 处，都没解决

**根本原因**：
1. 没有先验证后端是否正常工作
2. 没有观察后端日志确认请求是否到达
3. 混淆了前端和后端问题
4. 没有参考 ESP-IDF 官方示例

**正确做法**：
1. 浏览器直接访问后端接口验证
2. 观察后端日志确认请求到达
3. 根据日志定位具体问题
4. 参考官方示例修复

**经验**：
- **先验证再修复** 是最重要的原则
- 遇到问题不要猜测，要观察实际错误
- 参考成熟实现比自己写更可靠

### 关键发现

**`httpd_query_key_value` 解码不完整**：
- 解码了 `%20`（空格）、`%E4%B8%AD`（中文）等
- **但不解码 `%2F`（斜杠）**
- 必须手动调用 `url_decode()` 进行二次解码

**验证方法**：
- 浏览器直接访问后端接口，观察日志
- 如果日志显示 `原始路径: 'xxx%2Fyyy'` 但 `解码后: 'xxx/yyy'` 正常，说明修复成功
